# Проверка проекта и производительности — 9 сентября 2026

Приложение подходит для интерактивного анализа сохранённых кругов на проверенном компьютере. Найдено и исправлено заметное торможение SVG при больших массивах. Расчёты согласованы арифметически, но локальную дельту реальной телеметрии нельзя считать точной до миллисекунды: выравнивание расстояния остаётся приблизительным.

## Что изменено

- Отметки записанных пит-стопов и полосы составов шин под графиком стинтов. Пропуски времени не выдаются за пит-стопы. На узком экране шкалы пересчитываются по ширине, соседние подписи последнего круга не накладываются.
- Отдельные фильтры стинтов для левого и правого списков кругов. Сравнение разных кругов одного пилота поддерживается; одинаковый круг с обеих сторон нельзя случайно отправить из интерфейса.
- Номера пилотов, кругов, фильтры и корректные настройки сохраняются в URL. Кнопка Copy selection link копирует выбранную пару. Обновление страницы восстанавливает выбор; расчёт запускается кнопкой Compare laps.
- Реальные этапы ожидания, загрузки телеметрии и вычисления передаются сервером. Ошибку или оборванный поток клиент не считает успешным сравнением. Смена выбора отменяет ожидание на клиенте; уже начатая серверная обработка может завершиться и заполнить кэш.
- Дополнительный график передач. Тормоз остаётся бинарным сигналом, передача — ступенчатым.
- Для больших SVG-линий сохраняются первая, последняя, минимальная и максимальная точки каждого экранного столбца. Исходные точки, вычисления и значения курсора не сокращаются.
- Геометрия графика стинтов и статистика стинтов запоминаются между перемещениями курсора. Поиск положения по расстоянию на карте использует бинарный поиск вместо полного перебора.
- В примечаниях отчёта о шинах указан номер круга, включая сравнение одного пилота.

## Условия измерения

Windows, Intel Core i7-9750H, 12 логических процессоров, 32 GiB RAM, Node.js 24.20.0. Браузер приложения сообщает Chromium 152. Desktop viewport 1440×1200, DPR 1. Уменьшение CPU и сети не применялось. Были фоновые процессы; это локальные измерения, не лабораторная гарантия для всех устройств.

API запускался из `apps/api/dist/server.js` на порту 4001. Интерфейс проверялся из production-сборки. Измерения API: 1 прогревочный запрос и 30 последовательных запросов, включая чтение полного ответа. p95 — 95-й процентиль по ближайшему рангу. Время HTTP не включает отрисовку страницы.

## Отрисовка больших графиков

Отдельная страница собирает тот же `ChartCard` с production React. Одновременно открываются четыре графика по две линии, по 1 000 / 10 000 / 50 000 точек на линию. Синтетические массивы общие для графиков; 50 000 — размер каждой линии, не число уникальных объектов, умноженное на все графики. Генерация данных исключена из таймера монтирования.

Каждый размер получает 180 обновлений общего положения курсора, по одному на animation frame. Измерены время до React commit и интервалы между animation frames. Последние отражают плавность данного сценария, но **не являются INP, полной задержкой физического указателя или точными метками рисования пикселей**.

| Точек на линию | Интервал кадров до, медиана / p95 | После, медиана / p95 |
|---|---:|---:|
| 1 000 | 7,0 / 13,9 мс | 7,1 / 16,7 мс |
| 10 000 | 27,7 / 34,7 мс | 7,0 / 16,7 мс |
| 50 000 | 184,6 / 229,1 мс | 13,9 / 20,9 мс |

На 50 000 точек обновление React и до оптимизации укладывалось примерно в 1–2 мс, но интервалы кадров были очень длинными. Сокращение SVG-геометрии устранило основную задержку в данном сценарии. Время первого React commit на 50 000 точек уменьшилось с 141,3 до 26,3 мс. После оптимизации один из 180 интервалов превысил 34 мс; утверждать безусловно стабильные 60 FPS нельзя.

[До](profiling/ui-before.json), [после](profiling/ui-after.json). Числа относятся к этим конкретным запускам; небольшие различия на малом объёме не следует выдавать за статистически значимое ухудшение.

Проверка сокращения геометрии на 50 000 колеблющихся точек с одиночным пиком: отображается 2 298 точек при 600 столбцах, все минимумы и максимумы столбцов, края и одиночный пик сохранены; исходный массив остался из 50 000 точек. [Результат](profiling/display-reduction.json). Это сохранение экстремумов на масштабе пикселя, а не всех деталей внутри одного пикселя.

## Повторное открытие и память

90 циклов открытия/удаления четырёх графиков по 10 000 точек на линию, с паузами по 2 секунды — более трёх минут. Число DOM-элементов после каждого открытия постоянно: 181. Сообщаемая браузером JS-память менялась примерно от 15,2 до 47,4 MB; первый цикл — 19,4 MB, последний — 20,7 MB. Наблюдалось освобождение памяти, непрерывного роста в этом сценарии не обнаружено.

Это показания `performance.memory`, зависящие от браузера и сборщика мусора, без принудительного GC и снимков удерживаемых объектов. Результат не доказывает отсутствие любых утечек, расход GPU-памяти не измерен. [Длительный прогон](profiling/ui-endurance.json).

## Точность и границы выводов

Два модельных круга: длительности 100 и 102 с, дистанция 5 000 м; разные шаги исходных отсчётов 230 и 370 мс. Первый пример — постоянные скорости. Второй — скорость первого круга `v(t)=40+0.2t` м/с; второй круг проходит тот же профиль за время в 1,02 раза больше. Для второго примера эталонное время вычисляется независимо по формуле `t(d)=(-40+sqrt(1600+0.4d))/0.2`. Ожидаемая дельта в каждой точке — `-0.02*t(d)` секунд.

Проверялись функции фактического конвейера приложения: подготовка границ и интегрирование скорости, нормализация, выравнивание, минисектора. Максимальное расхождение локальной дельты с формулой: **0,9 мс** для постоянных скоростей и **1,585 мс** для ускорения. Здесь влияет округление расстояния до 0,1 м и интерполяция. В обоих примерах сумма минисекторов ровно −2 000 мс. Изменение сглаживания с 1 до 21 не изменило время, тормоз или передачи; промежуточных значений бинарного тормоза не возникло.

На девяти сохранённых реальных сравнениях расхождение формулы `leftTime − rightTime` с возвращённой дельтой и суммы минисекторов с итогом равно нулю в точности представленных данных. Это проверка согласованности, не независимое доказательство пространственной точности.

Дополнительная независимая сверка: по официальному времени окончания S1 и S2 первого круга найдена его дистанция на графике; оценочная дельта в этой точке сопоставлена с разницей официальных накопленных времён секторов. На 18 границах девяти сравнений максимальное абсолютное расхождение — **106,6 мс**. Границы не использовались для подгонки выравнивания.

Поэтому малые преимущества в отдельных минисекторах надо трактовать осторожно. Модельные 1,6 мс нельзя переносить на реальную телеметрию: разные траектории, дискретность, границы отсчётов и масштабирование длины дают дополнительную ошибку. На финише времена принудительно привязаны к официальному хронометражу — совпадение на финише не является независимой проверкой.

## Что проверено вручную

- Восстановление пилотов, кругов, фильтра стинта и настроек из URL; копирование ссылки.
- Фильтр MEDIUM меняет доступные круги и выбирает подходящий быстрый круг; старое сравнение сбрасывается.
- NOR L48 против NOR L49: дельта −0,089 с; отдельные круги одного пилота поддерживаются.
- Начало загрузки нового круга и смена выбора до ответа: устаревший результат не появляется.
- Квалификация сразу показывает выбор кругов, не показывает стинты; сравнение при шаге 7 м и сглаживании 5 работает.
- Передачи, педали, карта, клавиатурный курсор, минисектора и текстовый отчёт.
- На ширине 390 px страницы гонки и квалификации не имеют горизонтального переполнения; график стинтов сохраняет читаемый размер текста.
- API: разные сессии → 400, пит-круг → 422, чётное сглаживание → 400, неизвестный круг → 404. Потоковая ошибка передаётся отдельной записью `type: error`. Идентичный круг через JSON API математически даёт нулевую дельту; UI предотвращает случайный такой выбор.
- Сборка TypeScript и production-бандла.

Автотесты не добавлялись. Здесь сохранены измерительные сценарии и результаты, а не утверждение о полном покрытии всех возможных данных и отказов.

## Как повторить

1. `npm run build`.
2. В отдельном PowerShell: `$env:PORT='4001'`, затем `node apps/api/dist/server.js`. Это использует существующую локальную БД из `.env`.
3. `npm run profile:api` — записывает результаты API и численных экспериментов в `docs/profiling/api-and-accuracy.json`. Для другого порта перед запуском задайте `$env:PROFILE_URL='http://localhost:4000'`. Скрипт не удаляет кэши; прогрев может обновить совместимый результат до текущей версии приложения.
4. `npm run profile:ui`, затем открыть `http://127.0.0.1:4174`. Держать вкладку видимой. Выбрать Run profile или Run 3-minute endurance profile. JSON появится на странице; сохранить его отдельно перед следующим запуском.
5. Для сравнения до/после сохранять одинаковые размеры окна, число линий и параметры. Не запускать тяжёлые задачи параллельно с измерением. Для браузерного разбора отдельных задержек использовать Chrome DevTools → Performance → Record на production-странице; состояние памяти смотреть отдельно в Performance Monitor.

## Соответствие заданию

В приложении есть предметная логика: подготовка и кэширование временных рядов, интегрирование дистанции, сглаживание, линейная интерполяция, дельта и минисектора. Требование о больших графиках теперь подкреплено воспроизводимым синтетическим измерением; текущие реальные круги после выравнивания обычно содержат сотни точек. Не следует описывать искусственно плотную сетку как новую информацию от датчика.

Для текста диплома нужно привести эти условия измерений, формулы, контрольные примеры и ограничения. Следующее существенное улучшение точности потребует более строгой пространственной привязки и расширенной независимой валидации. Добавление аккаунтов или новых крупных разделов эту задачу не решит.
